# Design: `BGPVIPConfig` CRD — structured BGP API for VIP management (Tech Preview)

Date: 2026-08-07
Status: approved design (brainstorm 2026-08-07); spec pending user review
Jira: OPNET-595 Phase 3 item 1 (Tech Preview graduation criterion)
EP: openshift/enhancements#1982 — replaces the "API Extensions / structured
BGP API" Option A/B deliberation with a concrete Option B design

## Goal

Replace the Dev Preview configuration plumbing — the installer-generated
`bgp-vip-config` ConfigMap and the serialized-JSON
`ControllerConfigSpec.BGPVIPPeersJSON` user-facing role — with a single
admission-validated, typed, feature-gated API that carries the BGP VIP
peering configuration and provides the day-2 feedback loop (status
conditions) the Tech Preview graduation criteria require.

## Decisions (from brainstorm)

| Question | Decision | Rationale |
|---|---|---|
| Placement | **Option B: dedicated CRD** (EP's fallback, now primary) | Peer schema changed twice during Dev Preview and `config/v1` fields are permanent on arrival; a feature CRD gets its own status/conditions surface (TP criterion); `hostOverrides` on the fleet-watched Infrastructure object is exactly the fan-out the EP worries about. Designing B concretely also gives API review a real artifact to judge against Option A |
| API group | `machineconfiguration.openshift.io` | MCO is the primary renderer (peers file, static pods); the group already carries node-config CRDs. CNO watching an mcfg CRD is unusual but harmless |
| Version | `v1alpha1` | openshift/api convention for gated, still-maturing CRDs; promoted with the feature |
| Scope/name | Cluster-scoped singleton, `metadata.name == "cluster"` (CEL) | Matches config-object convention; one BGP VIP config per cluster |
| Password | **Inline `password` field only** (no secret support now) | User decision: BGP TCP-MD5 password is not treated as a security issue at this time; may change later. MetalLB's `BGPPeer` CRD has the same inline field (precedent for API review). The field is optional and independent, so an optional `passwordSecretRef` can be added later without breaking compatibility. **This amends the EP's TP criterion text** ("including passwordSecretRef") — secretRef becomes a pre-GA follow-up |
| VIPs | **Not in the CRD** | `apiVIPs`/`ingressVIPs` duplication from the Dev Preview JSON is dropped; consumers read VIPs from the Infrastructure CR (single source of truth) |
| Dev Preview path | **Deleted outright in the same change-set** | The gate is NoUpgrade in both Dev and Tech Preview; no migration needed. The EP's "GA removes the ConfigMap path" line moves up to TP |

## The CRD

`bgpvipconfigs.machineconfiguration.openshift.io/v1alpha1`, cluster-scoped,
gated `+openshift:enable:FeatureGate=BGPBasedVIPManagement` (the gate itself
is promoted DevPreviewNoUpgrade → TechPreviewNoUpgrade as a separate,
ordering-independent change).

```go
// BGPVIPConfig carries the BGP peering configuration for BGP-based VIP
// management (enhancement openshift/enhancements#1982). Singleton named
// "cluster"; generated by the installer from install-config
// platform.baremetal.bgpVIPConfig and editable day-2.
type BGPVIPConfigSpec struct {
    // localASN is the autonomous system number the cluster's FRR instances
    // run under.
    // +kubebuilder:validation:Minimum=1
    // +kubebuilder:validation:Maximum=4294967295
    // +required
    LocalASN int64 `json:"localASN"`

    // defaultPeers are the BGP peers every node sessions with, unless the
    // node is named in hostOverrides.
    // +listType=map
    // +listMapKey=peerAddress
    // +kubebuilder:validation:MinItems=1
    // +kubebuilder:validation:MaxItems=16
    // +required
    DefaultPeers []BGPVIPPeer `json:"defaultPeers"`

    // communities are BGP community strings attached to the VIP
    // advertisements ("n:n" classic or "n:n:n" large communities).
    // +listType=atomic
    // +kubebuilder:validation:MaxItems=8
    // +optional
    Communities []string `json:"communities,omitempty"`
    // per-item CEL: self.matches('^[0-9]+:[0-9]+(:[0-9]+)?$') plus numeric
    // range check on each segment (<= 4294967295)

    // hostOverrides replaces (does not merge with) defaultPeers for the
    // named nodes. Only the MCO-rendered per-node peers file consumes
    // overrides; the cluster-wide FRRConfiguration rendered by CNO uses
    // defaultPeers (documented Dev/Tech Preview limitation, carried over).
    // +listType=map
    // +listMapKey=hostname
    // +kubebuilder:validation:MaxItems=256
    // +optional
    HostOverrides []BGPVIPHostPeers `json:"hostOverrides,omitempty"`
}

type BGPVIPHostPeers struct {
    // hostname of the node (RFC 1123 subdomain; matched against the
    // node's hostname as resolved by baremetal-runtimecfg).
    // +kubebuilder:validation:MaxLength=253
    // +kubebuilder:validation:XValidation: RFC 1123 subdomain regex
    // +required
    Hostname string `json:"hostname"`

    // +listType=map
    // +listMapKey=peerAddress
    // +kubebuilder:validation:MinItems=1
    // +kubebuilder:validation:MaxItems=16
    // +required
    Peers []BGPVIPPeer `json:"peers"`
}

type BGPVIPPeer struct {
    // peerAddress is the IP of the BGP neighbor (IPv4 or IPv6; the
    // session's address family follows it).
    // CEL: isIP(self)
    // +required
    PeerAddress string `json:"peerAddress"`

    // +kubebuilder:validation:Minimum=1
    // +kubebuilder:validation:Maximum=4294967295
    // +required
    PeerASN int64 `json:"peerASN"`

    // password is the TCP MD5 password (RFC 2385) for the session,
    // in clear text. Kernel limit is 80 bytes.
    // Deliberately inline (matches MetalLB's BGPPeer API); a secret
    // reference variant may be added as an alternative later.
    // +kubebuilder:validation:MaxLength=80
    // +optional
    Password string `json:"password,omitempty"`

    // +kubebuilder:validation:Minimum=1
    // +kubebuilder:validation:Maximum=65535
    // +kubebuilder:default=179
    // +optional
    Port int32 `json:"port,omitempty"`

    // bfdEnabled enables BFD-backed failover for this session.
    // (Real boolean — fixes the Dev Preview "true"/"false" strings.)
    // +optional
    BFDEnabled *bool `json:"bfdEnabled,omitempty"`

    // +optional
    EBGPMultiHop *bool `json:"ebgpMultiHop,omitempty"`

    // holdTime/keepaliveTime use typed durations (fixes the Dev Preview
    // free-form strings). Struct-level CEL: when both are set,
    // holdTime >= 3 * keepaliveTime.
    // +optional
    HoldTime *metav1.Duration `json:"holdTime,omitempty"`
    // +optional
    KeepaliveTime *metav1.Duration `json:"keepaliveTime,omitempty"`
}

type BGPVIPConfigStatus struct {
    // observedGeneration of the spec last processed by MCO.
    // +optional
    ObservedGeneration int64 `json:"observedGeneration,omitempty"`

    // conditions:
    //  - "Rendered"          (owner: MCO)  — the per-node peers file
    //    content has been rendered into the MachineConfig / applied via
    //    the NodeDisruptionPolicy path
    //  - "SessionsConfigured" (owner: CNO) — the bgp-vip FRRConfiguration
    //    reflecting this spec has been applied
    // +listType=map
    // +listMapKey=type
    // +optional
    Conditions []metav1.Condition `json:"conditions,omitempty"`
}
```

No immutability rules beyond the singleton name: day-2 peer editing is the
feature. Validation summary: singleton-name CEL, ASN/port ranges, IP-typed
peer addresses, community format, list-map uniqueness (peers by address,
overrides by hostname), duration relation, size caps (16 peers per set, 256
overrides, 8 communities).

## Producers and consumers

### Installer (produces)

- install-config types (`platform.baremetal.bgpVIPConfig`,
  `hosts[].bgpPeers`) and their validation stay exactly as reviewed on
  openshift/installer#10718 — the user-facing install surface does not
  change. Type conversion: `bfdEnabled`/`ebgpMultiHop` strings →
  `*bool`, `holdTime`/`keepaliveTime` strings → `metav1.Duration`.
- The `bgpvipconfig` manifest asset renders a `BGPVIPConfig` manifest
  instead of the ConfigMap. The bootstrap node keeps the file-based path:
  the manifest file in the asset directory is read directly during
  bootstrap rendering (same pattern the ConfigMap manifest uses today).

### MCO (consumes; primary owner)

- The operator watches `BGPVIPConfig` (replacing the ConfigMap lister) and
  serializes the resolved spec into the **existing internal transport**,
  `ControllerConfigSpec.BGPVIPPeersJSON`. Templates and the
  runtimecfg contract (`frr-peers.json`, `render --peer-file`) are
  untouched — the JSON field's role shrinks from "user API" to "internal
  wire format", which is what mcfg-internal ControllerConfig is for. The
  JSON schema keeps `apiVIPs`/`ingressVIPs` populated by MCO from the
  Infrastructure CR (runtimecfg contract unchanged).
- Missing/deleted CRD on a BGP cluster: operator degrades and holds the
  last good ControllerConfig — identical semantics to today's missing
  ConfigMap (never blanks the peers file).
- Writes `status.observedGeneration` + `Rendered` condition.
- Ships a **NodeDisruptionPolicy** for the peers-file path (`none`
  action) so day-2 peer edits do not reboot or drain nodes (gap D6). After
  the bootstrap-to-CRD handover, the on-disk peers file only matters at
  early boot, so no-disruption is correct.

### CNO (consumes)

- Watches `BGPVIPConfig` instead of the ConfigMap; deletes the
  hand-mirrored `bgpVIPConfigData`/`bgpVIPPeer` JSON structs and imports
  the typed API (vendored openshift/api).
- Renders the same cluster-wide `bgp-vip` FRRConfiguration (sessions from
  `defaultPeers`, raw advertisement snippet unchanged); revalidation
  shrinks to cross-object checks only (admission now owns shape).
- Writes the `SessionsConfigured` condition. Condition writes from two
  operators to one status: each owns only its condition type; both use
  server-side apply with distinct field managers.
- The `hostOverrides` caveat (overrides affect only the per-node peers
  file, not the cluster-wide CR) carries over, now documented on the API
  field itself.

### Removal of the Dev Preview path

Deleted in the same change-set (per repo): installer ConfigMap asset, MCO
ConfigMap sync (`syncBGPVIPPeersJSON` ConfigMap read + bootstrap ConfigMap
manifest read), CNO ConfigMap read. The gate is NoUpgrade in both preview
sets, so no cluster can carry the old objects across an upgrade; no dual
path, no migration.

## Failure modes

| Scenario | Behavior |
|---|---|
| CRD instance absent on a BGP cluster | MCO Degraded (holds last good ControllerConfig); CNO leaves last FRRConfiguration, Degraded |
| Gate off, CR present | Consumers ignore it (gate check precedes informer handling); admission rejects writes when the gate is off (gated CRD not installed) |
| Invalid edit | Rejected at admission (CEL); no consumer ever sees invalid state — removes the Dev Preview "validate in every consumer" duplication |
| hostOverrides names unknown host | Rendered but unused (same as Dev Preview); runtimecfg falls back to defaultPeers for unmatched hostnames |
| Peer edit day-2 | MCO re-renders peers file without node disruption (NodeDisruptionPolicy); CNO re-renders FRRConfiguration; frr-k8s reloads sessions. VIP advertisement continuity governed by the existing gated-redistribution design |

## Sequencing and repositories

1. **openshift/api**: new CRD types + gated CRD manifest + integration
   tests (CEL). Independent: gate promotion Dev→TechPreview is a separate
   PR whenever graduation is due; the CRD works under either preview set.
2. **installer**: swap the ConfigMap asset for the CRD manifest (on top of
   #10718 or follow-up — decided at plan time).
3. **MCO**: watch swap + condition writes + NodeDisruptionPolicy (on top
   of #6326 or follow-up).
4. **CNO**: watch swap + typed import + condition (on top of #3047 or
   follow-up).
5. **EP amendment**: API Extensions section rewritten to the selected
   Option B with this design; passwordSecretRef TP criterion reworded to
   inline-now/secretRef-pre-GA; ConfigMap-removal moved from GA to TP
   criteria.

Whether steps 2–4 land as commits on the open Dev Preview PRs or as
follow-up PRs is a plan-time decision driven by review state at that
moment (the open PRs are review-gated; bolting the TP API onto them may
reset reviews).

## Testing

- **openshift/api**: integration tests for every CEL rule (singleton name,
  ranges, community format, duration relation, list-map uniqueness,
  MaxItems), following the api repo's test-suite convention for gated
  CRDs.
- **Consumers**: unit tests per repo (installer conversion incl.
  string→typed edge cases; MCO watch/serialize/degrade paths + condition;
  CNO render parity against the current ConfigMap-driven output — same
  FRRConfiguration bytes for equivalent input).
- **Live validation** (house practice, before any PR push): on the
  metal-u15 dual-stack cluster, hand-apply the CRD + CR, run the patched
  MCO/CNO images, verify: peers file identical to the ConfigMap-driven
  one, `bgp-vip` FRRConfiguration identical, conditions written, a day-2
  peer edit propagates without node disruption, and the full family-aware
  acceptance verify stays green.
- **CI**: the existing lanes cover the flow end to end once the consumer
  changes merge (the lane's install path exercises installer→MCO→CNO).

## Open items deliberately excluded (YAGNI)

- `passwordSecretRef` — future addition, shape reserved.
- Per-override communities/localASN — no use case surfaced in 28 runs.
- Status aggregation beyond the two conditions (e.g. per-node session
  state) — belongs to metrics/alerts (Phase 3 item 2), not this API.
- Non-baremetal platforms — EP Non-Goal 4.
